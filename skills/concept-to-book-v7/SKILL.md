# Concept to Book — Version 7

Establish choices before their dependent work scales; create the planned book, then revise and polish against observable goals. Recover existing decisions and valid work before adding process. This skill is standalone: all operational guidance, templates and optional local helpers are bundled. No earlier skill, private vault, publishing platform, particular builder, or Python runtime is required for the writing workflow. Optional helpers use Python 3 when available. Preserve versions 1–6.

V6 retains scoped preferences, connected pilots, drift/preservation checks, source-to-decision links, rework learning, project templates, quality rubrics, downstream priorities, mechanical checks, reader-feedback integration and release/session recovery. It adds six capabilities: composable project profiles; scene-level temporal continuity and knowledge; source-conflict/adaptation decisions; practical production adapters; format-specific reading/accessibility checks; and actual file-based integration tests.

V7 retains those capabilities and clarifies their execution order. Use [workflow-order.md](references/workflow-order.md) when coordinating the whole route or resuming several production streams. Interior assembly, physical cover assembly and their respective reviews have separate dependencies. A front-cover concept, an interior proof and an accepted interior-cover pair establish different things.

## Start at the actual stage and endpoint

Identify the requested deliverable: concept, outline, manuscript, illustrated proof, publication files, or an authorized publishing action. Audit current material against that endpoint and stop there. A request for writing or file preparation does not itself authorize uploads, reader contact, purchases, proof approval, or distribution.

Recover accepted direction, scoped exceptions, current files, and the highest evidenced state. Resolve superseded choices using the latest applicable explicit direction. A folder called Final, a transfer-progress display, or a catalog status does not identify an exact file version. Ask only when an unresolved choice materially affects the result; progress on independent work meanwhile.

Maintain one compact goal register: goal, evidence/priority, observable completion, current gap, and responsible stage A–L. Distinguish outcomes from tactics. Comparable development does not require identical word counts; less wasted space does not automatically require more art. An existing book does not need to restart to acquire a foundation.

## Select the relevant project profile

Read [project-profiles.md](references/project-profiles.md) when choosing the route for a new project or a changed scope. Combine original/adapted, standalone/series and text/illustrated dimensions as appropriate. Profiles select relevant questions, records and checks; they do not establish a creative preference, canon, tool choice, arbitrary numeric target or authority for production. Apply the requested endpoint first. Reuse the existing foundation when its choices remain valid.

## 1. Use practical project records

Read [project-records.md](references/project-records.md) when starting, migrating, or organizing a project. Adapt the bundled templates into existing project records. Use only relevant sections: a short outline can keep goals, settings, criteria, sources, issues, and next action in one brief. An illustrated series may need linked inventories and manifests. Do not create empty files simply to satisfy a template.

Keep records with the project, not inside the installed skill. Distinguish established choices, assumptions, candidates, unknowns, and not-applicable fields. Use stable IDs or precise locators where changes have downstream effects. Do not claim a check ran because a checkbox or template field exists.

## 2. Establish and calibrate the Book Foundation

Read [foundation-settings.md](references/foundation-settings.md) before substantial dependent work, or to fill relevant gaps in an existing project. Establish:

| Area | Decisions to establish early |
|---|---|
| Story | Audience, premise, original/adapted status, source boundaries, viewpoint, setting/time, world/cultural limits, arcs, local agency, reveals, climax and emotional ending |
| Craft and balance | Original voice, available influences actually read, humor/wonder, accessibility, explanation, punctuation, scene-depth benchmark, chapter experience, balance measure and quality/length priorities |
| Reader package | Per-book included/excluded/undecided sections, companions, prefaces, recaps, epilogue, afterwords, sources, profiles, maps and guides; purpose/order/knowledge boundary |
| Identity and references | Stable IDs, names/aliases, title policy, source edition and reading scope, citation/link presentation, supplied biography/photos, reliable metadata sources |
| Visuals | Style, coverage roles/density, appearance continuity, image shapes, maps/portraits, color strategy, source/derivative and preservation priorities |
| Editions and layout | Intended formats, chosen trim/binding/paper, typography, margins, furniture, chapter starts/blanks, placement, whitespace and preservation policy |
| Covers | Fixed logo/title/volume/author hierarchy versus permitted scene/cast/palette variation; spoiler ceiling; copy-surface roles, spine icons, portrait/branding, fit and contrast priorities |
| Completion | Endpoint, review coverage, acceptance criteria, current authority, exceptions, unresolved dependencies and their resolution milestones |

Separate preferences from later facts: final counts, actual delivered pixels, assigned ISBNs, exact spine/template geometry, manufacturing counts, real feedback, and platform acceptance must be obtained from evidence when relevant. Each deferral identifies why it is unknown, when to resolve it, and which action it blocks. Missing cover geometry does not block prose work.

Read relevant parts of [calibration-and-learning.md](references/calibration-and-learning.md) for author/series/book/edition scope, accepted and unwanted examples, overrides, drift and preservation. Explicit local direction governs its stated scope. A source recommendation or inferred preference is a candidate, not an author-wide instruction. Resolve concrete conflicts using the user's priorities; do not import the example project's exact values.

## Track story state and disclosure separately

Use [continuity-and-knowledge.md](references/continuity-and-knowledge.md) when time-sensitive facts, flashbacks, character knowledge or cross-book changes could cause errors. Keep stable scene/entity/topic IDs and distinguish story time from reading/disclosure order. Record when appearances, possessions, abilities and relationships become true or change, who knows each relevant fact, and the reader's knowledge ceiling at each disclosure point. Narrator access and uncertain inference remain explicit.

Extend existing canon records only where useful. State intervals and transitions need actual source/user evidence or labeled new fictional decisions. Unknowns remain unknown. A later character appearance does not retroactively change a childhood scene; a flashback's story time does not move its reader reveal earlier. Trace consequential changes into chapters, recaps, profiles, art, covers and review status.

The optional continuity checker inspects explicit structured declarations only; it cannot read prose for semantic truth or prove that a ledger covers every scene. Use manual inspection for unmodeled cases and confirm proposed contradictions against the authoritative text before repairing it. The bundled template is a starting point, not mandatory canon.

## 3. Define completion and prioritize by impact

Use [quality-and-priorities.md](references/quality-and-priorities.md) to turn subjective goals into observable criteria with examples, review method/scope, evidence, and reopen triggers. Distinguish required blockers, targets, preferences, optional improvements, and unresolved evidence. Avoid fake universal scores or thresholds inferred from examples. Record what a repair must preserve as well as what it should improve.

Prioritize uncertainties that could invalidate substantial dependent work, using actual dependencies and the requested endpoint. Identify blocked work and useful independent work. Group tasks only when they share outcome, authoritative inputs, and review scope. Do not turn prioritization into automatic commissioning of assets or production outside the request.

Use a connected pilot when interacting choices are uncertain and repetition would be costly. Carry the same representative unit through the applicable chain and requested endpoint; reuse accepted material, record completed/untested links separately, and adjust supported foundation choices before scaling. Select another unit only for an important uncovered condition. Skip a new pilot when valid evidence already answers the question. No extra approval gate follows from stage readiness.

## 4. Execute the complete book workflow

Read [outcome-stages.md](references/outcome-stages.md) for each stage's work, completion evidence, and reopen conditions. These are ownership groups, not twelve mandatory repeated passes or a strict alphabetical execution order. E/F/H/J/L preferences, including CD02/CD03 cover identity and edition strategy, belong in the foundation; later work executes or verifies them. The chronological route is in [workflow-order.md](references/workflow-order.md).

| Responsibility / stage | Work and result |
|---|---|
| Foundation — A | Establish the creative contract, scoped settings, reader inventory, criteria, sources and safe deferrals |
| Architecture — B | Research constraining questions and source variants; map arcs, story/read order, local agency, knowledge/reveals, setups/payoffs and chapter objective/resistance/turn/function |
| Creation — C | Draft the planned main and companion material at consistent depth; maintain continuity, sources and meaningful checkpoints |
| Development — D | Repair demonstrated gaps in agency, consequence, relationships, structure and endings; additions need an evidenced purpose or new user direction |
| Prose — E | Revise against original-voice criteria; improve execution while preserving protected emotional, factual and reveal qualities |
| Reader package — F | Complete canon-dependent prefaces, recaps, companions, afterwords, citations, identity and navigation against the inventory |
| Integrated reading — G | Review the required full reading scope, including supporting sections; reconcile canon and repaired material, with explicit coverage |
| Specification — H | Verify established format/layout/art/cover choices, available adapter capabilities and actual relevant requirements against representative proofs |
| Interior/reader assembly — I | Snapshot exact intended sources, metadata, fonts, asset versions and settings; create reproducible requested reading/interior outputs, including a digital front cover when requested |
| Visuals — J | Produce and integrate planned assets from stable briefs, checking source/appearance, knowledge limits, delivered pixels and placement |
| Rendered acceptance — K | Inspect actual pages/covers and requested-format reading behavior, group concrete defects, rebuild/recheck affected areas and neighbors, and record exact output evidence |
| Physical cover assembly/handoff — L | Assemble each wrap/jacket from real edition/template/interior facts at CD09; after its K review, match the exact interior-cover pair and report the requested files or authorized action at CD12 |

I/J can interleave as planned assets become ready; keep the source snapshot and affected outputs current. Verify the actual interior and relevant count/template inputs before calling a physical wrap final. When the interior changed after its last review, identify the cause and include the affected editorial/page-flow/navigation checks in the recovery plan; recovering its hash and count alone does not renew review coverage. L/CD09 assembly precedes that cover's K/CD10–CD11 rendered review and repair; L/CD12 handoff follows. An interior revision can reopen this chain for its affected edition. Do not postpone all companion writing or visual preferences until revision. Later polish should improve execution of the intended book, while allowing justified structural change or creative discovery.

At meaningful milestones, compare representative new work with scoped criteria and accepted examples. Intentional variation is not drift. A sample does not replace a required consecutive read or final rendered review. Audit before another pass: name the goal, actual gap, artifact/reading scope, needed reference, completion check and affected dependencies. Keep one issue register and retain valid unrelated evidence.

## 5. Integrate the full cover workflow

Read [cover-design-workflow.md](references/cover-design-workflow.md) when covers or jackets are in scope. Its twelve steps remain complete within this package:

CD05–CD08 may interleave when real copy, type and crop constrain each other. Use the actual intended copy and fonts for a fit claim; a placeholder or front-only preview leaves other surfaces untested. A partial cover-design request stops at its requested outcome without waiting for manufacturing facts needed only by a later wrap.

| Step | Timing and outcome |
|---|---|
| CD01 | Recover current direction and authoritative designs, inputs and edition files at entry/resumption |
| CD02 | Establish shared identity and permitted variation in the foundation |
| CD03 | Choose edition strategy early; obtain exact templates/counts/geometry when real inputs exist |
| CD04 | Brief and select story-specific imagery from stable canon and appearance evidence |
| CD05 | Test actual art/logo/type and demanding crops before scaling when useful; reuse valid pilot evidence |
| CD06 | Write distinct purposeful back/flap/identity copy within agreed spoiler and factual limits |
| CD07 | Fit source-grounded spine icons and supporting panels with actual-size optical balance |
| CD08 | Fit actual typography and repair contrast while preserving intended art, meaning and identity |
| CD09 | Assemble each edition independently against its applicable template and correct barcode/ISBN |
| CD10 | Inspect actual exported panels and series relationships at reading/print scale |
| CD11 | Diagnose individual technical defects; verify targeted repairs and honest derivative provenance |
| CD12 | Match the exact current interior-cover pair and distinguish receipt, validation, submission, processing, proof and distribution |

For technical repair, distinguish low-resolution scene art from excessive-resolution small icons/masks; use delivered pixels at actual placement, not requested dimensions or a changed DPI label. Permitted restoration must preserve originals and identify reconstructed detail. Structural preservation checks supplement rendered inspection. Exact typography, colors, objects, dimensions, brands and historical PPI limits in the case study are scoped examples.

## 6. Run mechanical checks when useful

Read [mechanical-checks.md](references/mechanical-checks.md) for the bundled optional checker, input schema and actual supported checks. Use it for explicit project inputs when mechanical errors could recur or invalidate outputs. Run only supported checks and retain findings against exact file versions. Use available equivalent tools or manual checks if Python is unavailable.

Automated evidence is limited to what was actually inspected: section declarations are not proof of correct narrative order, matching bytes are not proof of visual quality, declared dimensions are not measured embedded-PDF resolution, and a valid URL is not evidence its content was read. Font embedding, actual render/geometry checks and live platform validation need appropriate tools and actual evidence. Mark unsupported, unrun and unknown checks honestly; do not imply an all-clear from a subset.

No automatic fix, remote request or live action is implied. After a change, rerun affected checks and inspect plausible missing dependencies. Preserve checks whose relevant inputs demonstrably remain unchanged.

## Build with verified capabilities and inspect the requested formats

Read [production-adapters.md](references/production-adapters.md) when assembling actual outputs. Check the tool's current supported input/output contract before scaling, record tool/version/config and actual input/output identities, and distinguish requested capabilities from demonstrated ones. Prefer available suitable tools; missing support is an explicit gap, not permission to install dependencies or invent successful output. The bundled adapter supports a bounded local reading-edition workflow; its documentation names supported formats and limits.

Build into a new explicitly designated output location, preserving originals and prior releases. Do not silently truncate, drop unsupported content, change typography, rasterize text, or convert a local reading proof into a print-ready claim. Reconcile a requested format with the actual source capabilities. Artifact creation and inspection require their real inputs; an outline request remains an outline.

Use [format-reading-checks.md](references/format-reading-checks.md) for the actual requested output: reading order, navigation, semantic headings, meaningful image descriptions, reflow and available assistive-technology checks for digital reading; relevant typography, contrast, grayscale, cropping and small-size cover reading for print/marketing surfaces. Test the applicable output in available readers/renderers and record which conditions ran. XML/ZIP checks, the presence of alt text or a visually clean screenshot do not establish full accessibility or format conformance. Verify any applicable external standard/version and destination requirements when needed; do not reuse historical rules as current authority.

## 7. Integrate actual reader feedback

Read [reader-feedback.md](references/reader-feedback.md) when feedback exists or is requested. Attribute feedback to its real source and reading scope; separate actual readers, simulated reactions, and editorial inference. Record location/version, intended experience, observation, priority, proposed response and disposition. Do not contact readers without authorization.

Resolve conflicting reactions against the book's goals and scoped preferences, using concrete passages. Multiple readers noticing a problem does not make their proposed fix mandatory. Execute justified authorized revisions, record what must survive, and compare the result. Reopen affected reading/layout/source checks; leave unverified reader response pending instead of inventing approval. Independent cultural feedback remains distinct from model review.

## 8. Preserve source transparency and propagate changes

Whenever using references, follow [reference-provenance.md](references/reference-provenance.md). Log the exact source, origin, question, section/read scope, status, interpretation, actual application, destinations, limits and version-specific evidence. Tell the user when a new vault reference materially affects work. Distinguish consulted/applied from available/unread, unavailable or historically documented. With no vault, proceed from supplied material and state that no vault references were used.

Track consequential links: source/user direction → interpretation/scoped decision → affected text/assets/settings → verification evidence. Production reuse counts as a reference too. An imported study is not the source novel; internal canon is not real-world authority; established principles do not imply a fresh reread. Keep invented adaptation choices explicit.

When sources disagree, use [source-conflicts.md](references/source-conflicts.md) and its bundled decision template. Identify exact versions/passages and their actual scope, distinguish translation/retelling/tradition variants from contradictions, retain alternatives, and record the project's selected adaptation with its reason and uncertainty. Do not invent a consensus, rank all cultures by one source hierarchy, or present a fictional choice as verified traditional fact. A working adaptation can proceed under a clearly bounded choice; unresolved factual claims need the evidence required by their intended use. Apply the decision only to its scope and follow affected destinations.

Classify changes as repairs, refinements, deferred facts becoming known, or new direction. Follow the change-impact rules in the bundled outcome and cover guides. Check linked destinations and plausible omissions; a missing map is uncertainty. Preserve newer edits and unchanged valid evidence. Do not blindly replace historical records or rebuild unrelated editions.

## 9. Release, recover and learn

Use [release-and-recovery.md](references/release-and-recovery.md) at substantial handoffs, interruptions, release preparation or resumption. For small tasks a short current-state/next-action note suffices. Identify authoritative sources, exact outputs and reviewed versions, completed check coverage, pending issues, latest supported external state and next concrete action. Preserve a recoverable previous release and describe changes; do not overwrite current work with an old checkpoint.

Compare actual inputs with the checkpoint before resuming. Recover new work and uncertain state before retrying actions. Distinguish ready local files from actual receipt and full-pair validation. A release package records evidence; it does not grant publication authority or certify unperformed checks.

At delivery report goal status, outputs, criteria/review evidence, references actually used, unresolved dependencies and exact edition state. Record supported causes of substantial rework and a few scoped lessons. New information and valuable discovery are not automatically preventable failures. Promote inferred lessons only when evidence and user direction support the scope; do not silently alter global preferences or this skill. Stop at the requested endpoint.

## Maintain the skill separately from book production

After consequential skill edits, use [skill-evaluation.md](references/skill-evaluation.md) and the bundled synthetic cases to inspect actual behavior. Keep evaluation criteria out of blind executor inputs, results outside fixtures, and passed/failed/blocked/unrun distinct. Skill evaluation is not another mandatory book pass.

For changes to production or continuity integration, use [integration-testing.md](references/integration-testing.md). Exercise a small representative fixture through the actual supported files, including supporting sections, available art/cover inputs, manifests, checks and handoff. Introduce controlled source/metadata/asset changes and demonstrate updated dependencies, preserved unaffected work and prior releases. Compare input/output identities and inspect actual outputs. Plans, mock receipts and isolated unit checks do not establish that the complete chain ran. Record production, semantic, visual, reader and platform coverage separately; no live publication is authorized by a test. Run only materially affected cases after repairs.
