# Project records and reusable templates

Use this reference when starting, migrating, or resuming a project. The templates below are reusable output material, not six mandatory files. Keep records with the book project, never inside the reusable skill. Merge useful fields into an existing brief, inventory, ledger, manifest, issue list, or handoff; preserve its IDs, links, accepted decisions, and history. Create a separate file only when it makes the project easier to use.

## Select the smallest useful record

| Record | Use when | Copyable template |
|---|---|---|
| Book Foundation | Establishing the endpoint, decisions, priorities, or deferred dependencies | [Foundation](../assets/templates/foundation.md) |
| Reader-section inventory | Planning or checking which reader-facing units belong in each book | [Section inventory](../assets/templates/section-inventory.md) |
| Source ledger | Consulting a source, tracing its application, or auditing past use | [Source ledger](../assets/templates/source-ledger.md) |
| Asset manifest | Selecting or integrating images, fonts, templates, or other production inputs | [Asset manifest](../assets/templates/asset-manifest.md) |
| Issue register | Tracking a concrete gap, feedback, repair, or safe deferral | [Issue register](../assets/templates/issue-register.md) |
| Handoff and recovery record | Delivering, pausing, transferring, or recovering work | [Handoff](../assets/templates/handoff.md) |

For an outline-only request, a brief with the endpoint, necessary decisions, outlined units, actual sources used, and material open questions can be enough. Do not create empty asset, printer, release, or feedback records. A finished outline can have a compact handoff without ISBNs, manuscript hashes, artwork, or final-production facts.

## Adapt and reconcile

1. Find the existing records and authoritative project files. Recover explicit user decisions before filling gaps. A filename containing “final” or the newest modification time does not establish authority.
2. Reuse existing fields and IDs. Add only information needed by upcoming work or a real downstream dependency. If records disagree, establish which decision supersedes which within its scope; retain unresolved conflicts honestly.
3. Copy the relevant template section into the existing record, or link an existing field that already answers it. Do not replace populated records with blank templates or maintain duplicate competing versions.
4. Keep exact source/destination locations and evidence links where another agent would otherwise have to guess. Stable scene/section/asset IDs survive renaming and reflow; version-specific page numbers are supplementary locators.
5. Update consequential decisions and affected work together. Retain a short supersession note for changed requirements; do not rewrite historical source consultation or previously evidenced release status.

Use `Unknown`, `Not applicable`, `Unrun`, or a specific deferred status instead of fabricated completeness. A useful deferral names the missing fact, why it can wait, who or what resolves it, the resolution milestone, and the work it blocks. An owner can be a role or pending input; do not invent an assigned person.

## Keep states distinct

- **Decision:** established, working assumption, candidate, deferred, or superseded. Record explicit direction separately from inference or source advice.
- **Section or asset:** planned, in progress, ready for review, selected, integrated, omitted, or superseded as applicable. Selection does not prove integration or acceptance.
- **Check:** passed, failed, blocked, unrun, or not applicable, tied to its method, coverage, and reviewed version. A partial read remains partial even if no issue was found.
- **Source:** consulted, applied, available but not consulted, unavailable, or historical use documented. Identify an excerpt, secondary note, or report as such; it does not establish full primary-source reading.
- **Issue:** open, in progress, blocked, resolved, deferred, or accepted exception. Keep severity separate from workflow state; a deferred blocker still blocks its dependent commitment.

These labels are examples of useful distinctions, not a compulsory database schema. Preserve an equivalent existing vocabulary when its meanings are clear. All examples in these resources illustrate decisions; they establish no book canon, accepted user preference, universal quality threshold, or publishing fact.
